# Triplex в Pixso с GigaCode CLI

Плагин ставит LightBox из подключённой библиотеки Triplex. GigaCode CLI предлагает компоненты экрана, а плагин вставляет их экземпляры в выбранную область после подтверждения.

## Запуск на рабочем компьютере

Если в окне остаётся старая версия, откройте манифест, который фактически подключён в Pixso. Проверьте файлы по путям `main` и `ui` относительно этого манифеста. Если сборщик пишет в отдельную папку, проверяйте выходные файлы. В заголовке окна и под выбором размера должна быть версия 23.11.1. Если обновился только заголовок, Pixso получил новый JS, но загружает старый HTML.

1. Для локального запуска подключите `manifest.json` из этой папки. Он загружает корневые `main.js` и `ui.html`. Если используете отдельный dev-проект, замените оба файла по путям из его манифеста и перезапустите dev-сервер. Закройте и снова откройте плагин. Под выбором размера должна появиться надпись «Сборка UI 23.11.1».
2. Проверьте, что установленный CLI доступен в терминале. Плагин рассчитан на [GigaCode CLI](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/). Для проверки выполните `gigacode -p "Ответь словом OK" --output-format json`. Ожидается JSON с полем `result`. Авторизация выполняется в самом CLI.
3. Запустите `node gigachat-bridge.mjs`. Скопируйте код подключения из терминала в плагин. Это код локального моста, он меняется при перезапуске. Мост слушает только `127.0.0.1:43127`, а запрос передаётся в CLI через аргумент `-p`.
4. Поставьте LightBox и выделите внутренний фрейм с автолейаутом. Если выделен сам LightBox, плагин ищет единственный `BodyPage` среди первых двух уровней.
5. Опишите задачу и нажмите «Предложить компоненты». Плагин передаёт все компоненты библиотеки установленного LightBox, кроме кнопок, и сопоставляет их назначение со справочником Triplex. Для набора вариантов он использует вариант по умолчанию.
6. Обсудите предложение в чате и нажмите «Подтвердить набор компонентов». Для каждого компонента согласуйте свойства и тексты. После последнего подтверждения нажмите «Добавить на фрейм». Ошибки и состояния на этом этапе не предлагаются.

[Storybook Triplex](https://triplex-design.ru/next/ru/Web) и [исходники Triplex Next](https://github.com/SberBusiness/triplex-next) описывают назначение и поведение компонентов. Плагин получает экземпляры и свойства через каталог Pixso. Модель получает справочник назначения компонентов, а вставлять может только доступные экземпляры из каталога Pixso.

Если CLI отвечает из терминала, а окно Pixso не подключается, проверьте разрешение редактора или браузера на доступ к локальной сети. Плагин отправляет описание задачи и имена и назначение предложенных компонентов. Учётные данные GigaCode остаются в CLI.

## Верстка, состояния и ошибки

1. После вставки компонентов расставьте их на фрейме и настройте размеры в Pixso.
2. Нажмите «Закрепить верстку». Исходный фрейм блокируется для редактирования. Для правок используйте «Изменить верстку», затем закрепите макет повторно.
3. Нажмите «Предложить состояния и ошибки». До первого успешного ответа поле уточнений скрыто. Только теперь модель впервые предлагает ошибки, варианты и состояния на основе кейса и фактических компонентов на фрейме. Проверяются обязательность, формат, диапазон, зависимости, сеть, сервер и другие применимые случаи; неподтвержденные бизнес-правила помечаются как гипотезы.
4. Возле каждого состояния и каждой ошибки переключите «+ Берём / − Не берём». После первого ответа появится поле уточнений и кнопка «Дополнить предложения». Дополните описание кейса и запросите дополнительные предложения. Решения для совпадающих состояний и ошибок сохраняются.
5. Нажмите «Утвердить состояния и ошибки», затем «Создать выбранные состояния рядом с фреймом». Плагин копирует закрепленный экран рядом с исходным, сохраняет размеры фрейма и компонентов, применяет доступные варианты и свойства. Исключенные ошибки и соответствующие им варианты не добавляются.

Условия и сообщения ошибок также видны под каждой копией. Если библиотека не предоставляет текстовое свойство ошибки, сообщение остается в этой подписи для ручного оформления. Недоступный вариант останавливает создание и удаляет незавершенные копии. Изменение исходной верстки требует повторного закрепления и согласования состояний.

Кнопки исключены из каталога. При подборе компонентов модель должна обосновать выбор типов; специализированный компонент или отображение готовых данных нельзя автоматически заменять TextField. Ограничение каталога семью семействами удалено. Неизвестные компоненты остаются доступными, но их назначение требуется уточнить.

## Проверка

`node --test tests/workflow.test.cjs` — проверки каталога, этапов UI, закрепления макета, выбора ошибок, размеров копий и отката при ошибке. Используются заглушки Pixso; для интеграционной проверки необходимы Pixso, подключенная библиотека Triplex и авторизованный GigaCode CLI.

## Знания о дизайн-системе (21.11.4)

`knowledge/triplex-components.json` содержит 137 описаний — по одному для каждого раздела компонентов официального Storybook, проверенного 21.11.4026. У каждого описания есть назначение, при необходимости отличие от похожих компонентов, ссылка на Storybook и официальный исходник. Это контекст для GigaCode, а не изменение весов модели. Описания составлены по документации Triplex; исходники библиотеки в плагин не включаются.

Примеры различий: AmountField вводит деньги, Amount показывает готовую сумму; NumberField вводит количество; MaskedField работает с заданным форматом; SelectField выбирает одно значение, MultiselectField — несколько, SuggestField предлагает варианты по вводу. Учтены также таблицы, списки, карточки, типографика, загрузка файлов, структура и навигация. Служебные React-компоненты описаны как невизуальные.

Справочник встраивается в `main.js`, поэтому плагин работает без отдельного запроса к документации и без настройки MCP в GigaCode. После изменения JSON выполните:

```sh
node scripts/sync-triplex-knowledge.mjs
node scripts/sync-triplex-knowledge.mjs --check
node --test tests/workflow.test.cjs
```

Назначение и ограничения передаются при подборе, правках в чате, настройке текстов и запросе состояний. Каталог связывается со справочником по точному имени/псевдониму, сначала по имени компонента, затем по контейнеру и категории. Например, Text не совпадает с TextField. Дочерние варианты набора не дублируются в каталоге, если Pixso вернул их ключи вместе с набором.

Важно различать документацию и доступность: знание компонента не добавляет его в библиотеку Pixso. Источником доступных экземпляров остаётся библиотека установленного LightBox; свойства берутся из Pixso, а не из React props. Неизвестные имена отмечаются явно, в окне показывается число сопоставлений. Полный список доступных ID не обрезается: если каталог, история и краткие назначения превышают лимит моста 48 000 символов, плагин сообщает об этом. Дополнительные пояснения различий добавляются в оставшийся бюджет.

## Правки набора в чате

При изменении состава модель должна передать полный новый список. `uid` обозначает существующее поле, `id` — тип из каталога. Пара `uid` и новый `id` заменяет тип существующего поля; отсутствие `uid` в итоговом списке удаляет поле. Настройки неизменённых компонентов сохраняются, изменённые компоненты проходят подтверждение заново.

Новый набор становится текущим только после проверки и успешного импорта всех замен. Текстовое «заменил» без применимых изменений не считается успехом. Пока правки не применены, подтверждение и вставка заблокированы. Можно повторить запрос, уточнить его или явно нажать «Оставить текущий набор без правок».

В UI текущий набор показан отдельными строками с подписью и типом компонента. Список применённых изменений формирует плагин сравнением наборов, а не из утверждений модели. Регрессионный тест B2B проверяет удаление BodyPage/Island, замену MaskedField на TextField и SuggestField, последующее подтверждение и вставку исправленного набора.

В 21.11.4 обработка подписи принимает `text`, а также `label`/`title` как альтернативные имена поля. Переносы строк и лишние пробелы нормализуются. При замене существующего компонента отсутствующая подпись сохраняется из предыдущего набора. Для новой строки подпись не выдумывается: при ошибке формата выполняется один запрос исправления к модели, затем выводится конкретный номер строки и причина. Слишком длинный текст не обрезается молча.

В 21.11.5 формат правок нормализуется перед проверкой. `catalogId` и `componentId` принимаются как синонимы `id`; повторённые `name`, `confirmed`, `reason` и другие известные описательные поля не применяются как настройки. Явные `remove:true` / `action:delete` / `operation:remove` удаляют строку по uid. Структурные `updates` разворачиваются в полный набор с сохранением незатронутых строк. Противоречивые ID и неизвестные операции не игнорируются: выполняется одна попытка исправления ответа моделью, затем показывается конкретная причина. При ошибке прежний набор остаётся целым, а переход дальше заблокирован до решения пользователя.

## История диалогов файла (23.11.1)

Откройте «История диалогов этого файла» в верхней части окна. «Обновить историю» показывает сохранённые диалоги с названием задачи, этапом и временем изменения. Нажмите название, чтобы открыть переписку и продолжить работу. «Новый диалог» сохраняет текущий сценарий и начинает отдельный. Установка нового LightBox также начинает отдельный сценарий, если текущий уже связан с фреймом.

Автосохранение записывает данные в pluginData корня файла Pixso: историю сообщений, требования и текстовый стандарт, набор компонентов и подтверждённые настройки, незавершённые тексты, черновик свойств, шаг согласования, состояния и выбор «берём / не берём». Код подключения к GigaCode не сохраняется. После перезапуска моста может потребоваться ввести его заново. Запрос к модели, прерванный закрытием окна, автоматически не повторяется; его можно отправить снова с сохранёнными данными.

При открытии плагина показывается список истории. Данные доступны в этом файле, а не глобально для всех файлов пользователя. Экземпляры компонентов восстанавливаются по ID или ключу библиотеки. Если исходный фрейм удалён или библиотечный компонент недоступен, история открывается только для чтения без перезаписи сохранённого сценария. После восстановления фрейма или библиотеки откройте диалог повторно. Изменённый после сохранения макет нужно закрепить заново перед созданием состояний.

Большие записи сохраняются частями; указатель на новую запись обновляется после записи всех частей, поэтому ошибка сохранения не уничтожает предыдущую версию. Ошибки хранения отображаются под историей. Диалоги, закрытые до появления этой функции, автоматически восстановить невозможно.
