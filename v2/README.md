# ChatToDesign v2

Новая версия находится в ветке `codex/plugin-v2` и папке `v2`. Корневые `manifest.json`, `main.js`, `ui.html` и старые архивы сохранены без изменений. История v2 хранится отдельно от истории v1.

## Запуск в Pixso

1. Подключите **`v2/manifest.json`** как отдельный локальный плагин. У него отдельные имя и ID: `ChatToDesign · v2`.
2. Запустите `node v2/gigachat-bridge.mjs`. Если прежний мост уже работает, можно использовать его; второй процесс на том же порту не нужен.
3. Выберите размер формы. Плагин автоматически поставит LightBox. При ошибке появится «Повторить попытку».
4. Введите код подключения из терминала в поле «Токен GigaCode CLI» и опишите задачу.
5. Проверьте компоненты, удалите лишние или отправьте задачу на доработку. Подтвердите набор.
6. Согласуйте свойства каждого компонента. Превью показано слева и автоматически обновляется после изменения свойств (пауза 300 мс при вводе). «Назад» сохраняет черновик и возвращает к предыдущему компоненту, а с первого — к набору.
7. В финальном наборе «Назад» открывает свойства последнего компонента. «Поставить на макет» вставляет согласованные экземпляры.

После вставки доступен этап состояний компонентов и ошибок. Библиотека Triplex и авторизация GigaCode CLI требуются как в прежней версии. Код локального моста не сохраняется в истории.

## Макеты

Источник: [Figma](https://www.figma.com/design/SyMMFR1cBGIDu5Z5b3xYQ2/Untitled?node-id=1-2).
Реализованы компоненты Select, Text Field, Text Area Field и Button, включая loading, и экраны выбора размера, задачи, предложения, доработки, свойств и итогового набора. В свойства добавлена обязательная область живого превью из Pixso. Шрифты SB Sans используются при наличии в системе, иначе Arial.

## Проверка

Из корня проекта:

```sh
node --test tests/workflow.test.cjs tests/v2-workflow.test.cjs
node tests/v2-ui-smoke.cjs
```

Второй сценарий требует Playwright и установленный Google Chrome. Он проверяет реальный DOM и переходы с подставными ответами Pixso: выбор размера, повтор установки, загрузку, подбор, доработку, запрос превью, подтверждение и возврат. Скриншоты сохраняются во временные файлы `/tmp/v2-*.png`.

Интеграционная проверка реальной библиотеки и вызовов CLI выполняется в Pixso; автоматические проверки используют заглушки API.

## Исправление доработок и скорости превью

Точечные изменения `updates` принимаются на этапе списка и при ответе `action:list` без полного `items`; незатронутые компоненты сохраняются. Ответ с прежним набором или только текстовым заявлением о замене отправляется модели на автоматическое исправление один раз. После повторной неудачи прежний набор остаётся неподтверждённым; ложное сообщение об успешной замене не показывается.

Успешные PNG превью кешируются по экземпляру библиотечного компонента и значениям полей (до 6 изображений, суммарно до 512 КиБ PNG). При неизменных настройках повторное открытие не создаёт временный экземпляр. Для новых настроек экспорт ограничен 640 px по длинной стороне. Неизменённые значения свойств не отправляются в `setProperties`. Во время ввода старое превью сохраняется до нового ответа; отдельная отмена на каждый символ больше не отправляется. Временные экземпляры по-прежнему удаляются после экспорта, в том числе при ошибке.

## Состояния после вставки

1. Расставьте компоненты на исходном макете и нажмите «Добавить состояния компонент».
2. Выберите «Посмотреть предложенные GigaCode» для автоматического подбора либо «Предоставить аналитику», введите правила и нажмите кнопку добавления состояний. Аналитика передаётся отдельно от исходной бизнес-задачи и имеет приоритет для бизнес-правил и текстов ошибок.
3. Варианты сгруппированы по компонентам: каждая ошибка и каждое состояние показаны отдельным настоящим превью. Значение и ошибка записаны внутри компонента. Превью загружаются автоматически и обновляются после правки текста. В «Изменить текст» можно поправить значение или ошибку и исключить вариант.
4. «Подтвердить» создаёт отдельные экземпляры компонентов рядом с исходным экраном, по колонке на каждый компонент. Копии всей формы и внешние подписи ошибок не создаются. Неотрисовываемые варианты пропускаются, их незавершённые копии удаляются; успешные варианты сохраняются. В результате показано количество добавленных и пропущенных вариантов. Старые сохранённые предложения следует запросить заново для перехода на этот формат.

При первом запросе сохраняется сигнатура исходной верстки, исходный фрейм блокируется. После изменения исходного макета предложения нужно запросить заново. До первого запроса исходный экран можно свободно расставлять. Тексты, выбранный сценарий и аналитика сохраняются в истории файла; код подключения не сохраняется.

Плагин передаёт GigaCode фактические свойства и совместимые варианты каждого экземпляра. Раскрытый Select и активный ввод включаются при наличии однозначного свойства BOOLEAN или подходящего варианта. Если в библиотеке нет такого представления, это отмечается в ответе; текстовое описание не выдаётся за раскрытый компонент. Варианты с другой темой или размером отклоняются. Некорректный ответ о состояниях автоматически исправляется моделью один раз.

Для ошибки отдельно применяются error-статус и текст. Текст помещается прежде всего в Description, затем в явно доступное Error/Validation-свойство. Для библиотеки без такого свойства поддерживается единственный однозначный вложенный текстовый слой Description; изменение делается только на копии, с загрузкой его шрифтов. При неоднозначной структуре сообщение остаётся в подписи к копии, а интерфейс указывает ограничение.

Проверенные источники структуры Triplex:
- [TextFieldBase: поле и отдельный FormFieldDescription](https://github.com/SberBusiness/triplex-next/blob/main/src/components/TextField/TextFieldBase.tsx)
- [FormField: active и status](https://github.com/SberBusiness/triplex-next/blob/main/src/components/FormField/FormField.tsx)
- [SelectField: target и dropdown](https://github.com/SberBusiness/triplex-next/blob/main/src/components/SelectField/SelectField.tsx)

React API описывает поведение; он не используется как перечень доступных свойств Pixso. Источником доступности остаётся подключённая библиотека. Радиопереключатели используют оригинальные SVG из Figma; они встроены в HTML, поэтому UI не обращается к временным URL.

## Текстовый стандарт и редполитика

В `v2/knowledge/editorial-policy.json` собраны 23 правила с привязками к публичным разделам [Triplex Super Text](https://triplex-design.ru/next/ru/Super/Text/release%20notes) (релиз текстового стандарта 7.3.2, проверен 23.11.2026) и страницам предоставленной редполитики СберБанк Онлайн (v31 по имени PDF, экспорт 18.12.2025). В метаданных сохранён SHA-256 исходного PDF; сам PDF и полный текст страниц не копируются в сборку.

Правила автоматически включаются в каждый запрос GigaCode, в том числе исправление некорректного ответа. Для этапа подбираются соответствующие выдержки: подписи и placeholders при настройке, ошибки и валидация при состояниях. Контекст правил занимает менее 4000 символов. Он учитывается внутри общего лимита 48000; реальные ID каталога и история ради него не обрезаются. При превышении лимита запрос останавливается с объяснением.

Профиль по умолчанию — Triplex / СберБизнес. Для явно указанного в задаче СберБанк Онлайн / СБОЛ применяется профиль СБОЛ. Различия сохранены: например, Triplex отделяет процент пробелом и завершает полные предложения в ошибках точкой, СБОЛ не ставит пробел перед `%` и точку в конце последнего предложения. Явное указание `Профиль: sbol` или `Профиль: triplex` в текстовом стандарте также выбирает профиль. Общие правила СБОЛ дополняют Triplex, но не заменяют его канальное оформление.

Справочник не переписывает вручную подтверждённые тексты и дословные тексты аналитики без запроса пользователя, не меняет состав компонентов и JSON-протокол. Внутренний каталог системных ошибок, на который ссылается публичная страница Triplex, не загружен; модель не должна выдавать свои предложения за тексты из него. Это контекст генерации, а не автоматическая редакторская проверка каждого ответа.

После изменения JSON:

```sh
node v2/scripts/sync-editorial-policy.mjs
node v2/scripts/sync-editorial-policy.mjs --check
node --test tests/workflow.test.cjs tests/v2-workflow.test.cjs
```

Готовая сборка содержит правила внутри `v2/main.js` и не требует доступа к PDF или сайту Triplex во время работы плагина.

### Сопоставление вариантов состояний

Модель получает только совместимые варианты каждого поля и `variantOptions` с библиотечными `key`. Проверка и применение используют один resolver: точный ключ или полное имя, затем однозначное сопоставление значения состояния либо набора осей. Порядок осей и регистр не меняют идентичность. `Disabled`, `Filled`, `Selected` и подобные оси разрешены как состояния; `Property 1` распознаётся как состояние только для известных значений вроде Default/Focus/Error. Размер, тема и остальные оси сохраняются. Неоднозначность, неизвестный ключ и противоречие ключа и имени возвращаются на исправление; первый похожий вариант не выбирается. Ошибка указывает компонент и фактическую причину, а не универсальный запрет размера/темы.

### Сохранение согласованных текстов

Ручные изменения подписи, подсказки и значения синхронизируются между реальными свойствами компонента и его описанием для GigaCode. Перед подбором состояний считываются актуальные тексты с холста, включая вложенные слои Label/Description; старые подписи из pluginData не имеют приоритета над ними. Правки через чат также применяются к реальным свойствам, а не только к карточке.

При смене варианта копии сохраняются тексты экземпляра: сначала по точному ключу, затем по однозначному имени без суффикса Pixso или семантической роли. Для вложенных слоёв сохраняются их значения; статусы фокуса/раскрытия/ошибки выбранного варианта не сбрасываются прежними boolean-значениями. Если перенос неоднозначен, создание останавливается вместо молчаливого возврата библиотечного текста.

Ручные правки ошибок и значений в карточках сохраняются, если последующий ответ модели повторяет прежний текст. Состояния без отличий от макета исключаются, одинаковые варианты объединяются. Модель получает требование предлагать конкретные взаимодействия и подтверждённые проверки без придуманных лимитов; это контекст генерации, а не гарантия качества каждого предложения. В списке видны значения и сообщения ошибок, а технический ответ модели не выводится вместо пояснения результата.

### Комбинации осей State / Filled / Error

Для библиотеки с независимыми осями `State`, `Filled`, `Warning`, `Error` плагин принимает изменения осей (`axes`) и готовые `stateCapabilities.controls`. Из совместимых кандидатов выбирается единственный вариант с минимальным изменением остальных осей текущего экземпляра. Равнозначные кандидаты не выбираются наугад. Например, `State=Active` не отклоняется из-за `Error=False`; для ошибки отдельно выбирается `Error=True`. При активном вводе учитывается заполненность поля, при ошибке пустого поля — `Filled=False`. Размер и `Darkmode` остаются прежними. Пустое необязательное имя не мешает валидному ключу или набору осей; пустая запись варианта при явной ошибке поля заменяется выбором его настоящего error-состояния.
